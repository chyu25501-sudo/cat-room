## 4. 技術スタックの選定理由と自習計画（AI主導開発への最適化）
### フロントエンド
- **採用技術**：Vite + React (TypeScript) + Tailwind CSS + Web Audio API
- **AI主導開発の観点からの選定根拠**：
  - **SSR起因のハルシネーション・エラー完全回避**：Next.js（App Router）では、サーバーとクライアントの境界（`use client`）や、ブラウザ専用API（`window`, `AudioContext`, `PointerEvent`）の取り扱いにおいて、AIがSSRエラー（`window is not defined` 等）を誘発しやすく、デバッグループに陥るリスクがあります。完全なSPA（Single Page Application）である **Vite + React** を採用することで、AIが音声処理やポインター描画コードを迷いなくシンプルに生成できます。
  - **爆速のフィードバックループ**：Viteは起動・ビルドが極めて高速なため、AIエージェントがターミナルで `npm run build` やテストを実行して自己検証・修正を行う際のイテレーション時間を大幅に短縮できます。
  - **Tailwind CSS**：コンポーネント内にスタイルを完結できるユーティリティクラスは、CSSファイルを跨いだAIの編集ミスを防ぎ、一貫したUI生成を実現します。

### バックエンドおよびデータベース
- **採用技術**：Supabase (PostgreSQL)
- **AI主導開発の観点からの選定根拠（Cloudflare D1、Tursoとの比較）**：
  - **コード記述量の最小化**：BaaS（Backend as a Service）であるSupabaseを採用することで、APIエンドポイント（サーバー側ロジック）を個別に自作する必要がなく、フロントエンドから公式SDK（`@supabase/supabase-js`）で直接データ保存・取得を行えます。AIが書くべきコード総量が減るため、バグ混入のリスクが劇的に下がります。
  - **LLMの学習データ量とコード精度**：Cloudflare D1やTursoと比較して、Supabaseは世界中で圧倒的な導入実績があり、AI（LLM）のコード生成精度・ベストプラクティスの遵守率が最も高い技術です。
  - **TypeScript型連携によるAIの自己修正**：Supabaseのスキーマから型定義（`Database`型）を自動生成できるため、AIがTypeScriptのコンパイルチェック（`tsc --noEmit`）を通じて、カラム名のタイポや型の不整合を自律的に検知・修正できます。

### ホスティング環境
- **採用基盤**：Vercel
- **AI主導開発の観点からの選定根拠（Cloudflare Pages、GitHub Pagesとの比較）**：
  - **ゼロコンフィグ＆自動デプロイ**：GitHubリポジトリへのプッシュに連動して即座にビルド・公開され、AIが生成したリポジトリ構成のまま手動設定なしで本番稼働します。
  - **エラーログの明瞭さ**：デプロイ失敗時のログが具体的かつ分かりやすいため、エラー内容をそのままAIにフィードバックして迅速に自己解決させることができます。

### 人間側の自習計画（AIディレクション・マネジメント学習）
コードを人間が手書きするのではなく、**「AIに正しく作らせ、検証し、本番へ届けるディレクション能力」** を習得する計画とします。
- **第1〜2週**：AIへの要求仕様の伝え方（プロンプティング）、ボタンと音声再生の最小構成をAIに作らせる指示方法、Git/GitHub連携とVercelへの初回デプロイ確認。
- **第3〜4週**：AIが生成したコードの動作確認手法（ブラウザの開発者ツールでエラーやAudio再生状態を確認する方法）、AIへの的確なバグ修正指示の出し方。
- **第5〜6週**：Supabase管理画面（Table Editor、SQL Editor）の基本操作、AIに安全なDBテーブル定義（DDL）を出力させて適用する手順の習得。
- **第7〜8週**：AIにテストコード（Vitest）を書かせ、自動検証ハーネス（`npm run verify`）を通過させる品質マネジメントの習得。


## 5. 8週間の垂直スライス開発計画（AI主導アプローチ）
毎週、人間が「仕様指示・動作検証・デプロイ承認」を行い、AIが「実装・テスト作成・自己修復」を担当して、画面〜DB〜配備までが一気通貫で動く動線を作ります。

- **第1週：【環境構築・初公開と音出し（最小垂直スライス）】**
  - **利用者シナリオ**：利用者が公開URLにアクセスすると、シンプルな画面の中央に「猫を呼ぶ（鳴らす）」ボタンが表示されている。ボタンを押すとスピーカーから「ニャー」と猫の鳴き声が再生される。
  - **AI実装タスク**：Vite + React (TypeScript) + Tailwind CSSのプロジェクト初期化、Web Audio API（またはAudio要素）による鳴き声の再生機能、Vercelへの本番自動デプロイ（初週でのWeb公開完了）。

- **第2週：【猫のシルエット表示と直接タップによるふれあい・回数保存】**
  - **利用者シナリオ**：画面中央に猫のシルエット（イラスト）が表示される。猫の体を直接タップ（クリック）すると「ニャー」と鳴き、画面上の「ふれあい回数」が1回増えてブラウザ（localStorage / 状態管理）に保存され、ページを再読み込みしても回数が維持される。
  - **AI実装タスク**：猫のシルエットSVGコンポーネント化、タップ領域のクリックイベント処理、カウントのローカル永続化（localStorage）、Vercel更新。

- **第3週：【撫でる動作（ドラッグ/スワイプ）の検知とSupabase連携】**
  - **利用者シナリオ**：利用者が猫の体を指やマウスでスーッとなぞる（撫でる）と、指の動きを検知して「ゴロゴロ…」と喉を鳴らす音が再生される。撫でたストローク量（総スキンシップ数）がカウントアップされ、クラウドデータベース（Supabase）へ永続保存される。
  - **AI実装タスク**：Pointer Events（移動ベクトル・距離計算）ロジック、喉鳴らし音声ループ制御、Supabaseプロジェクト接続とログ保存テーブルへの書き込み。

- **第4週：【猫のご機嫌ステータスとリアクション変化】**
  - **利用者シナリオ**：利用者が優しく撫で続けると、猫のご機嫌ゲージが上昇し、ステータスが「ふつう」から「ごきげん」に変化する。シルエットが嬉しそうに揺れ、鳴き声も甘えた声に変わる。現在の猫のご機嫌ステータスがDBに保存され、後からアクセスしても引き継がれる。
  - **AI実装タスク**：ステートマシン（普通・ご機嫌・怒り）の状態遷移設計、CSSアニメーション（揺れ・ハート等）、状態に応じた音声分岐、DB同期。

- **第5週：【撫ですぎによる「怒り」とクールダウンの導入】**
  - **利用者シナリオ**：利用者が短時間に激しく撫ですぎると、猫が嫌がって「シャーッ！」と威嚇し、背を向ける（怒り状態）。怒っている間は撫でても受け付けなくなり、利用者は少し時間を置くことで機嫌が治るのを待つ。怒られた回数と最新状態がDBに記録される。
  - **AI実装タスク**：短時間での撫で頻度・過剰判定アルゴリズム、怒りリアクション演出、クールダウンタイマーと復帰ロジックのDB永続化。

- **第6週：【お世話アクションボタンの実装（ごはん・おもちゃ）】**
  - **利用者シナリオ**：利用者が画面下の「ごはんをあげる」「ねこじゃらしを振る」ボタンを押すと、猫が専用のリアクション（食べる音やじゃれる動き）を見せる。怒っている猫にごはんをあげて機嫌を直すことができ、実行したお世話履歴がDBに保存される。
  - **AI実装タスク**：アクションボタンUIコンポーネント、各アクションのアニメーションと効果音、怒り状態の解除ロジック、アクション履歴テーブル連携。

- **第7週：【なつき度（親密度）レベルと特別リアクションの解放】**
  - **利用者シナリオ**：日々のふれあいやお世話の積み重ねにより、「なつき度レベル」が1から2へ上昇する。レベルが上がると、猫がお腹を見せて甘える特別なポーズや新しい鳴き声が解放され、画面上にレベルバッジが表示される。
  - **AI実装タスク**：経験値・レベルアップ計算ロジック、アンロック機能のフラグ管理、特別ポーズSVG/CSS演出、ユーザー進行度テーブル更新。

- **第8週：【ふれあい記録の可視化・総合演出と完成版公開】**
  - **利用者シナリオ**：これまでに撫でた総回数や喜んだ回数が振り返れる「きろく」画面、BGMや環境音のオン/オフ機能、スマートフォンの触覚フィードバック（バイブレーション）、猫への命名機能が整い、誰でも直感的にいつでもどこでも猫と心を通わせられる癒やしアプリとして正式完成・公開される。
  - **AI実装タスク**：Supabase集計クエリ・統計カードUI、スマホ向け触覚フィードバック（Vibration API）、全体スタイリング調整、パフォーマンス最適化、最終リリース配備。


## 6. ハーネス設計と品質管理方針（AI自律稼働のためのガードレール）
### 自動テスト・検証ハーネス（AIの自己検証ループ）
AI主導開発では、AI自身が「コード生成 → テスト・型検査実行 → エラー検知 → 自己修正」を自律的に繰り返せるコマンド体系（検証ハーネス）を整備することが最重要です。

- **ワンライナー検証コマンドの導入**：
  - `package.json` に `npm run verify` スクリプトを定義：
    ```bash
    npm run verify = "tsc --noEmit && biome check . && vitest run"
    ```
  - AIには「コード編集後、必ず `npm run verify` を実行し、全チェックがGreen（エラー0）になるまで修正を完了すること」を義務付けます。
- **テストフレームワークと対象領域**：
  - **単体テスト（Vitest）**：猫のご機嫌度・怒り判定の計算、ストローク距離の計算、レベルアップ判定などの純粋ロジック。AIが生成したロジックが仕様通りか高速検証。
  - **コンポーネントテスト（Vitest + React Testing Library）**：猫の状態に応じたUI描画、ボタンのクリックイベント発火の検証。
  - **E2Eテスト（Playwright）**：実際のブラウザ操作（クリック・撫でるドラッグ操作）を行い、画面表示とデータ保存が正しく結合動作しているかを自動検証。

### エージェント規範定義の導入計画
- **配備方針**：リポジトリ内にエージェント規範定義ファイル（`.gemini/rules` や `AGENTS.md` 等）を常設し、AIが開発方針から脱線しないための強い制約を明文化します。
- **規範ルールの方針**：
  1. **決定論的アーキテクチャの遵守**：
     - ブラウザAPI（Web Audio API, Pointer Events）を直接コンポーネント内に散らかさず、専用のカスタムフック（例: `useCatAudio`, `useStrokeDetector`）に隔離すること。
     - 純粋な計算ロジック（機嫌計算など）は純粋関数として別ファイル（`utils/` または `domain/`）に切り離し、AIが100%テスト可能な構造にすること。
  2. **TypeScript厳格モードの徹底**：
     - `any` 型の使用を禁止し、Supabaseのテーブル型定義と連動した厳密な型付けを行うこと。
  3. **小さな垂直スライスの維持**：
     - 一度に大量のファイルを変更せず、1機能ごとに「UI ⇄ ロジック ⇄ データ保存 ⇄ テスト通過」のサイクルを守ること。
  4. **自己検証義務**：
     - 作業完了を人間に報告する前に、必ず `npm run verify` をターミナルで実行し、型エラーやテスト失敗がないことを確認すること。
